*模型：Meshy-6；纹理分辨率 2K。*

在重建一个茶水间时，我们希望用真实照片改善地面的材质。照片里的地面是浅灰色，带着细小颗粒和零星白色斑点。设想很直接：把这张照片交给 Meshy，为已有地面生成 PBR 材质，再贴回 Blender。

然而，Meshy 返回的基础颜色贴图接近黑色。把它应用到房间后，原本灰色的地面也变得几乎漆黑。

![原场景灰色地面与 Meshy 黑色地面的房间视角对比](/images/meshy-floor-2026-10-10/teaser.png)

*房间内的效果对比：左侧是重建场景原有的 `floor_vinyl` 灰色地面，右侧是第一次 Meshy 生成的黑色地面。两张图使用同一相机、灯光和曝光，其他模型及材质保持一致，仅替换地面材质及必要的 UV。左侧并非真实照片，也不是后文“带墙代理”的生成结果。*

照片明明是灰色，为什么生成结果会变成一块黑色面板？这是一次随机失败，还是输入模型和生成参数造成的稳定偏差？我们先重复生成，再把代理模型与去光照开关拆开做对照。

结果有一个值得注意的转折：**关闭去光照并没有让薄盒恢复灰色；换成带两面墙的代理后，地面却从黑色变成了灰白色。** 这让我们重新审视“参考照片如何约束材质生成”这个问题。

## 起点：照片、代理模型与一套生成参数

<div style="float: left; width: 35%; max-width: 210px; margin: 0.35rem 1.25rem 0.9rem 0;">
  <img src="/images/meshy-floor-2026-10-10/reference.png" alt="真实地面参考照片" style="width: 100%; border-radius: 4px;">
  <p style="margin: 0.45rem 0 0; font-size: 0.78rem; line-height: 1.5; font-style: italic; opacity: 0.75;">图 1：真实地面照片。它记录的是受现场照明影响的表面外观，不能直接当作经过校准的材质本色。</p>
</div>

这次调用的是 Meshy 的 Retexture 接口：输入一个已有 3D 模型和一张参考图，让系统重新生成纹理。基础颜色（Base Color）决定表面的颜色；PBR 还包含粗糙度、金属度和法线等信息，用来描述表面如何与光发生作用。

为了把材质生成与整个房间的复杂结构分开，我们最初提交了一个地面代理：**4 × 4 × 0.05 米的闭合薄盒**。“代理”是用于生成贴图的简化模型，生成后只把材质应用到实际房间的地面，代理本身不会进入房间场景。

薄盒带有不重叠的 UV，顶面占据主要贴图区域，底面和侧面放在边带中。UV 可以理解为把三维表面对应到二维贴图上的坐标。代理使用无贴图的灰色初始材质，GLB 中的颜色系数为 `[0.30, 0.32, 0.33, 1]`，金属度为 0，粗糙度为 0.5；这些颜色系数也不等同于照片里直接读取的 sRGB 像素值。

模型与照片分别通过 `model_url`、`image_style_url` 发送，其余参数如下：

<div style="clear: both;"></div>

```json
{
  "ai_model": "meshy-6",
  "enable_original_uv": true,
  "enable_pbr": true,
  "texture_resolution": "2k",
  "remove_lighting": true,
  "target_formats": ["glb"]
}
```

没有发送文字提示词，也没有发送房间的灯光、曝光或完整 Blender 场景。照片仅转换为 RGBA PNG 编码，没有调整颜色或亮度。

其中，`remove_lighting` 是“去光照”开关。按 [Meshy 官方文档](https://docs.meshy.ai/en/api/retexture) 的描述，它用于移除基础颜色贴图中的高光与阴影，便于模型在新的灯光下渲染。这个处理是否可能错误估计了灰色地面的本色，成为了我们后续要检查的一个假设。

## 第一轮：重复生成，检查黑色是否只是偶然

我们先用完全相同的照片、代理模型和参数追加两次独立生成。三次请求的内容指纹一致，任务 ID 各不相同，因此比较的是三个独立输出。

![相同输入的三次生成结果](/images/meshy-floor-2026-10-10/repeat_comparison.png)

*图 2：参考照片与三次生成的基础颜色贴图。只展示实际地面 UV 区域，没有加入 Blender 的灯光或曝光。*

为便于比较，我们从下载的 GLB 中提取嵌入的基础颜色图，取实际地面 UV 对应的区域，再对存储的 sRGB 编码值计算加权灰度指标：

```text
L = 0.2126R + 0.7152G + 0.0722B
```

表格和图中所称的“像素亮度”均指这个指标的中位数，范围为 0–255，数值越小，图片越暗。这里没有把 sRGB 解码为线性光强，因此它不是严格的光度学亮度，也不是物理反射率测量。参考照片包含现场照明，与生成贴图的差异只能用于描述颜色偏移，不能直接作为材质本色的定量误差。

| 样本 | 像素亮度中位数 |
|---|---:|
| 真实参考照片 | 174.0 |
| 第一次生成 | 23.1 |
| 重复生成 1 | 26.0 |
| 重复生成 2 | 22.1 |

三份结果都接近黑色，约 95.5% 的地面像素亮度低于 50。黑色已经存在于 Meshy 导出的基础颜色贴图中，因此 Blender 灯光无法解释这一生成异常。

我们也检查了其他通道。三份金属度贴图的中位数分别约为 0.59、0.17 和 0；即使金属度为 0，基础颜色仍然很黑。导出的颜色乘数都是白色 `[1,1,1,1]`，发光贴图在地面大部分区域也是零。这些检查降低了“额外颜色乘数压黑”或“关闭发光导致变黑”的可能性。

这一轮说明：**在当前照片和参数组合下，发黑连续出现三次，不能仅归为一次偶然。** 但我们没有由此估计出可靠的失败概率，也不能推断 Meshy 对所有灰色地面都会如此。

## 第二轮：把代理形状和去光照开关拆开比较

接下来，我们提出两个假设：

1. **代理形状影响了生成。** 薄盒可能给出了“面板类物体”的上下文，使系统为它重新设计外观，而没有忠实保留地面的颜色。生成图中还出现了参考照片没有的白色边框，这是一条值得追查的线索。
2. **去光照处理影响了颜色。** 系统可能错误估计了照片中的照明与材质本色，从而把基础颜色压暗。

为检查两者，我们做了四组对照，每组独立生成两次：薄盒／房间代理 × 去光照开启／关闭。

房间代理由同一个薄盒添加两面约 2 米高的墙得到，墙位于原地面边界外，并与地面合并成闭合模型。照片、灰色初始材质、原有 4 × 4 米地面及其顶面 UV 映射保持一致，其余 Meshy 参数也相同。新增墙面使用贴图边带。

![实际输入的薄盒代理与地面加两面墙代理](/images/meshy-floor-2026-10-10/proxy_comparison.png)

*图 3：左侧为原薄盒，右侧为替换后的房间代理。两者都由实际提交的 GLB 渲染而来，保留原灰色材质，使用同一相机、正交投影比例和摄影棚光照。这是输入几何的展示，未使用 Meshy 生成贴图；摄影棚灯光也没有作为 API 输入发送。*

单独查看：[薄盒代理图片](/images/meshy-floor-2026-10-10/proxy_box.png)、[地面加两面墙代理图片](/images/meshy-floor-2026-10-10/proxy_room_corner.png)。

| 对照项 | 薄盒代理 | 地面加两面墙代理 |
|---|---|---|
| 地面顶面 | 4 × 4 米 | 同一尺寸与顶面坐标 |
| 灰色初始材质 | 相同 | 相同 |
| 地面顶面 UV | 保留 | 保留相同映射 |
| 整体几何 | 闭合薄盒 | 添加两面墙并闭合连接 |
| 底面、侧面与墙面 UV | 边带中的独立区域 | 随新增表面重新分配边带 |

因此，这一实验检查的是**代理几何与上下文这一组变化**，没有把“语义理解”“整体形状”和“侧面 UV 布局”等内部影响逐一分离。

这里有一个设计调整：我们最初尝试过开放平面，但四份任务都在 78% 返回通用服务器错误，均未计费。API 没有给出具体原因，因此不能据此断言 Meshy 普遍不支持开放平面。为了获得有效的颜色样本，最终采用了闭合的“地面加两面墙”代理。

![代理模型与去光照开关的四组对照](/images/meshy-floor-2026-10-10/factorial.png)

*图 4：四组、八次独立生成的基础颜色贴图。每列是一种条件，上下两张为重复样本。四组都是本轮新提交的任务，没有用第一轮的旧结果代替本轮基线。*

| 代理模型 | 去光照 | 生成 1 的亮度中位数 | 生成 2 的亮度中位数 | 观察 |
|---|---|---:|---:|---|
| 闭合薄盒 | 开 | 27.6 | 20.6 | 接近黑色 |
| 闭合薄盒 | 关 | 1.0 | 1.0 | 更接近纯黑 |
| 地面加两面墙 | 开 | 255.0 | 255.0 | 几乎纯白 |
| 地面加两面墙 | 关 | 214.1 | 212.1 | 浅灰色，但细节很弱 |

最明显的差别发生在代理替换上：不论去光照开还是关，薄盒都保持黑色，带墙代理都变成了灰白色。去光照的方向则因代理而异：薄盒开启时比关闭时稍亮，带墙代理开启时几乎变成纯白。

我们核对了输出模型中实际地面的 UV 映射，确认八份统计都对应地面区域，没有误取墙面。Meshy 会归一化模型尺寸，并重排或简化部分墙面三角形，因此不能声称输入与输出的全部几何数组逐项相等；实际地面的 UV 映射则经过了单独验证。

本文用于定量分析的图 2、图 4 直接来自原始颜色贴图，不受这个相机问题影响。开篇的房间对比图则是后来重新渲染的：相机位于天花板下方、距地面约 2.07 米，采用高位斜俯视，并通过射线检查确认能看到实际地面。它用于展示材质应用效果，不参与像素统计。

## 结果支持什么，又没有证明什么？

**第一，在本次配置中，代理替换对生成颜色有很大的影响。** 同一张照片，在薄盒条件下四份结果都偏黑，在带墙条件下四份结果都变成灰白色。这个差异同时出现在去光照开、关两种条件中。

但“它把薄盒理解成了黑色面板”仍然只是猜测。加墙同时改变了整体几何、表面积分布和边带 UV 布局，内部的视角、采样或生成过程也可能随之变化。实验支持的是这组代理变化对结果的影响，尚不能定位到某个具体的语义识别机制。

**第二，不支持“开启去光照是薄盒发黑的主要原因”。** 关闭它后，薄盒并没有恢复灰色，反而更黑。因此，我们需要修正最初对去光照的怀疑。

不过，这个开关也并非对颜色没有影响：带墙代理关闭时是浅灰色，开启时几乎变成纯白。这提示它的效果依赖当前代理条件。每组只有两份样本，我们还没有做统计显著性检验，不能把观察到的组合效应当作已经建立的普遍规律。

**第三，避免黑色的结果仍然不准确。** 带墙、关闭去光照的输出虽然是灰色，但比参考照片更浅，细小颗粒也几乎消失。实验帮助我们定位了影响因素，还没有实现真实地面的材质复原。

## 最后的判断：把照片当作生成引导，而不是材质测量结果

结合这次实验，我们更倾向于把 Meshy Retexture 理解为：**以输入模型的几何结构和参考图为条件，生成新的表面外观，再通过 UV 映射到模型上。** 参考照片提供视觉引导，但不构成颜色和 PBR 参数的保真保证。

这一解释与接口用途相符。官方将 `image_style_url` 描述为引导纹理生成的二维图片，也提醒输入模型与图片存在较大几何差异时，效果可能不理想。[Meshy Retexture 文档](https://docs.meshy.ai/en/api/retexture)

“根据模型的理解来贴图”是一个便于描述行为的工作假设。我们观察到了几何上下文的强烈影响，却没有观察到系统内部的推理过程。能够确认的是：在这次测试中，照片并没有把地面的颜色牢牢约束住。

对需要还原真实场景的任务，生成结果仍需要检查：颜色是否偏移，颗粒尺度是否合理，粗糙度与金属度是否符合材料，以及换一套灯光后是否仍然可信。Meshy 生成的 PBR 可以作为起点，不能直接视为真实材料参数的测量值。

这次排查留下的实践经验是：**输入的简化模型也应尽量保留目标物体的结构上下文；验证材质时，先检查原始贴图，再检查它在场景中的表现。** 一个过于简化的代理，可能得到与目标表面相差很远的颜色；一个看起来不黑的结果，也仍可能丢失真实表面的纹理。

如果继续追查机制，下一步可以分别改变初始材质颜色、侧面 UV 布局或墙面数量，让这些变量逐个接受对照。它们尚未在本次实验中验证。

## 复现范围与实验输入

图 3 中的两种代理即为本次提交的原始输入模型：闭合薄盒与地面加两面墙；生成用的参考照片见图 1。

本次测试没有指定随机种子。同组重复使用相同请求内容，但独立提交任务；不同任务 ID 能说明没有复用同一个任务结果，不能证明我们控制了系统内部的全部随机性。四份失败的开放平面任务没有可用纹理输出，因此未纳入颜色统计。

---

**实验规模与成本：** 初始一次生成 10 积分，第一轮两次重复 20 积分，第二轮八份有效对照 80 积分；本次地面排查合计 110 Meshy 积分。四份失败的开放平面任务均为 0 积分。所有结论限定于这张照片、这些代理模型以及本次 Meshy-6／2K 配置。
